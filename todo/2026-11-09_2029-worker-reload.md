## Goal

Activate Orchestra code changes without shutting down a WSL distribution or interrupting unrelated workloads; let an executing controller activity finish before replacing its worker.

## Authority register

- **D1:** Support updates without restarting WSL. Reason: restarting it breaks other workloads.
- **D2:** Search primary web sources and choose a flexible KISS solution. Reason: not stated.
- **D3:** Investigate, verify with architect, then implement the change. Reason: not stated.
- **Q1 — CLOSED by D2:** Must every Python process keep its identity forever? The clarified requirement concerns the distribution and unrelated workloads; the mechanism is delegated under D2.
- **A1 — ACTIVE:** Gracefully replacing Orchestra processes meets D1. This is a design choice, not an operator requirement for a particular mechanism.
- **A2 — ACTIVE:** The deployment caller may wait for current activities, with their existing deadlines, rather than adding a background deployment service. If that caller dies, a later start/reload completes activation.

## Non-goals

Generic Python module hot reload; automatic code watching; restarting Temporal for source changes; dependency upgrades; preserving manually initiated agent conversation turns during process replacement; changing workflow commands or run snapshots; modifying WSL or host configuration.

## Verified evidence

- [Worker entry point](../app/interfaces/worker.py) imports its Python modules once and hosts activities, workflows on WSL, and the terminal server. Native agent CLIs already start afresh for each controller turn.
- [Stack owner](../app/application/stack.py) and [host mechanics](../workers.sh) already operate on individual processes, not the distribution. Current restart forcibly stops workers and can interrupt activities.
- [Windows mechanics](../workers.ps1) preserve unelevated launch and verify the recorded worker before stopping it.
- [Terminal containment](../app/agents/docs/architecture/structure.md) deliberately ends agents with their worker. Removing that guarantee would create orphans.
- [Temporal's native Worker API](https://python.temporal.io/temporalio.worker.Worker.html) provides shutdown and a graceful activity interval. Installed SDK source stops polling, waits for activities and flushes completions before returning.
- [Python reload documentation](https://docs.python.org/3/library/importlib.html#importlib.reload) warns about retained references and thread safety.
- [Microsoft WSL commands](https://learn.microsoft.com/windows/wsl/basic-commands) distinguish process execution from terminating a distribution or shutting down the VM.
- Initial Git working tree was clean. No live service was changed during investigation.

## Current architecture and source of truth

[Root architecture](../docs/architecture/structure.md), [application composition](../app/application/docs/architecture/structure.md), and [interface composition](../app/interfaces/docs/architecture/structure.md) own the relevant invariants. Stack remains the only lifecycle controller. Native Temporal shutdown owns draining; workflow history remains the authority for run progress.

## Problem and root cause

The platform does not require a WSL restart. The missing operation is a non-destructive way to activate fresh worker imports: existing restart can kill healthy turns. Blind module reload would mix generations of Python objects while activity threads are executing.

## Decision

### Premise / KISS

Extend the existing stack owner with `reload`, targeting workers only. Request native graceful shutdown through PID-scoped local runtime files; wait for that worker to exit; reuse existing cleanup, launch and polling proofs. Give the native activity grace its largest supported duration, verified through real SDK tests, so reload imposes no practical shorter turn deadline. No new service, process supervisor, port, credential, dependency, workflow command or automatic retry is introduced. One small file watcher exists because host scripts must request shutdown on both Windows and Linux without relying on incompatible signal behavior. Current force stop/restart remains explicitly destructive.

The deployment caller remains alive while draining (A2); instant activation and preservation of arbitrary manual terminal work are knowingly dropped. Workbench already has a separately scoped systemd restart; browser assets and settings use their existing owners. All Python layers become fresh through process replacement, rather than selected-module reload.

### Alternatives considered

| Option | Added moving parts | Consequence |
|---|---|---|
| Native drain under existing stack lifecycle | Two PID-scoped runtime files and one worker watcher; existing scripts and lock | Selected; preserves current activities and containment |
| In-place Python reload | Module dependency graph, locks and generation tracking | Cannot safely cover all layers or existing object references |
| Overlapping worker generations | Supervisor, terminal port routing, generation health and retirement | Unnecessary for D1; substantially larger failure surface |
| Distribution restart | None in Orchestra | Violates D1 |

## Required invariants

- Never invoke WSL termination/shutdown or stop unrelated services during reload.
- Never force-stop an executing worker during reload, including unreadable status, failed requests or interrupted callers.
- Refuse unsupported old workers before stopping them; an initial idle, targeted process restart may bootstrap support.
- Stop polling through Temporal itself; preserve current activities, heartbeats, session identifiers, run snapshots, single-attempt effects and history replay.
- Prove the old worker gone before cleanup/replacement, then prove the new worker polls its assigned queues.
- Preserve stack locking, private-policy isolation, unelevated Windows preflight, stale-setting sweep, duplicate prevention and process-tree containment.

## Rollout and rollback

Local implementation and isolated tests first. Already running workers do not gain this code by editing files: bootstrap each affected worker only when idle, using its existing process controls. Never restart the distribution. Subsequent reloads drain automatically. If a caller ends during draining, inspect the worker and use start/reload to finish; never fall back to force restart. Startup failure stays visible and requires fixing the cause before another start. Existing runs keep their snapshots. Live activation is outside the local verification claim.

## Completion criteria

Targeted code refresh preserves executing controller activities and unrelated processes; new worker imports and assigned polling are proven; refusal paths mutate no protected process; documentation and required host checks pass. Report bootstrap and live activation separately.

## Review record

Investigation: verified existing process-only lifecycle and identified forced worker stop as the actual gap. No production edits in this phase.

Architectural review: PASS for this plan against the current owners and consumers. Native shutdown preserves single-attempt activities; no workflow command changes require patching. Two runtime files are process-control state, not workflow state. Force-stop remains separate. Real SDK grace acceptance, failure-path tests and both host suites are implementation gates; the plan alone proves none of those runtime claims. D3 requests the ordered implementation phase after this check.

Implementation review found a necessary sequencing correction: retiring the workflow worker alongside its activities prevented queries during a long drain. The cohosted query regression failed with its expected timeout, then passed when shutdown was ordered activity-first. Native cancellation also reaches the draining activity; the zero-grace known-bad control interrupts it. Tests cover request refusal, unknown process state, an interrupted caller, a worker appearing before cleanup, and original-PID death checks after pid-file deletion.

Final review strengthened cleanup at the native script boundary: a newly appearing worker must not enter force stop after the controller checked for death. The real-process Windows regression first failed because cleanup killed its stand-in worker, then passed with idle-only cleanup. WSL's corresponding regression passed too. Both full suites had passed before this correction (816 WSL, 581 Windows); final replacement gates verify this last behavior change.

A Windows file-sharing regression then reproduced a concurrent capability reader preventing the worker from publishing drain status. Capability now stays immutable during its lifetime, duplicate requests do not rewrite a held request file, and status projects the PID-scoped request rather than pretending it proves SDK shutdown has already begun. The regression passed on Windows and WSL.

Native tests use the SDK's disposable server and scripted activities, never a model. Test-owned workflows disable caching because the legacy time-skipping server left a retired sticky queue pending; production workflow caching is unchanged. These tests establish draining and handoff, not production sticky-cache latency or live deployment acceptance.

Final host acceptance: `bash run-tests.sh` passed 818 tests in 164 classes; `powershell -NoProfile -ExecutionPolicy Bypass -File run-tests.ps1` passed 583 tests in 115 classes. Suites ran sequentially. Bash and PowerShell syntax checks, Make target dry runs, 38 local documentation link targets and `git diff --check` passed. Public-check passed, including its known-bad control, tracked files, index and history; the two new public files also passed a separate Gitleaks scan. Live workers were not activated; existing processes remain running.

Final architectural review: PASS for the local implementation and its bounded evidence. Lifecycle ownership, containment, workflow authority and run snapshots remain intact. No generic module reload, service supervisor, dependency, network port or workflow-history change was added. The operational bootstrap and live activation remain separate from this verification.
