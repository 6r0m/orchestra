## Goal

An iteration on a change runs, in seconds rather than minutes, exactly the tests that change can
reach — the whole suite only when the change reaches everything or cannot be attributed — and a whole
run takes about as long as its slowest part, not the sum of all of them.

## Authority register

### Operator decisions

- **D1** Run the suite's modules in parallel.
  - Effect: `make test` and the host suites run modules concurrently rather than one after another.
  - Reason: not stated; asked after a full run of the suite had taken about eight minutes per review round.
  - Date/source: 2026-09-23, operator — *"we need yes parallel run"*
- **D2** Run the whole suite when core code changed; otherwise only the exact modules the change affects.
  - Effect: the selection rule of [Decision](#decision); what counts as core is A1.
  - Reason: not stated.
  - Date/source: 2026-09-23, operator — *"run all suite if core changed otherwise only exact modules"*
- **D3** An iteration does not run the huge checks every time: only the scope of the module being
  changed, following the industry's standard practice for quick, quality iterations.
  - Effect: the selected run is the inner loop's default; the whole suite is the gate at the end of a
    change, not after each step.
  - Reason: *"quick and quality iterations"*
  - Date/source: 2026-09-23, operator

### Operator gates

- **Q1 [OPEN - NON-BLOCKING]:** how many modules run at once — default while open: A2.
- **Q2 [OPEN - NON-BLOCKING]:** what a selection is measured against — default while open: A3.
- **Q3 [OPEN - BLOCKING]:** the evidence ([what a static import graph would select](#verified-evidence))
  shows D2's selection, read from imports, would run 70–96% of the suite's time for nearly every file in
  `app/`. Which should it be? — gates: tasks 1 and 3.
  - **(a) As D2 says, from the import graph.** Always correct, with small savings: it mostly skips the
    cheap modules.
  - **(b) Test-level impact analysis traced from coverage** (pytest-testmon). More precise, but it adds
    pytest and coverage, a second runner and a database, and it is blind to the subprocesses (workers,
    PTY host, fake agents) where this suite's risk lives.
  - **(c) Parallel only, now; selection decided after task 4 has measured the parallel whole run.** If
    classes in parallel bring the whole suite near a minute, selection saves little. While iterating,
    an agent keeps naming the modules it changed (`bash run-tests.sh tests.x.test_y`), and the whole
    parallel suite is the gate.

  The investigation's suggestion, for the reviewer to weigh on their own evidence rather than take as
  decided: (c) now, and later, only if a whole parallel run is still too slow, (a) done the way the large
  shops make it pay — by first narrowing what the shared harness imports, so each test module depends
  only on what it uses (see [Review record](#review-record), the industry practice). Not (b).

### Working assumptions

- **A1 [ACTIVE]:** "Core" is not a hand-kept list. It is whatever the import graph says every test module
  reaches (today `app/foundation`, the shared harness `tests/temporal_env.py` and the policy it loads),
  plus any changed file the graph cannot attribute to a test module: a script, a data file, a file
  launched by path rather than imported. Either one runs the whole suite.
- **A2 [ACTIVE]:** at most `min(cpu count, 8)` modules at once, so the wall-clock bounds some tests
  assert keep their margin.
- **A3 [ACTIVE]:** a selection is the working tree against `HEAD`, untracked files included; `--since
  <ref>` measures against another commit, as a branch before its merge is.
- **A4 [ACTIVE]:** what runs in its own process is a test class, not a module: `test_stops` alone takes
  210 s, so modules in parallel could not bring a whole run under about three and a half minutes. A
  selection still chooses modules; the runner splits each chosen module into its classes.
- **A5 [ACTIVE]:** a Stop's cleanup bound, `STOP_CLEANUP`, comes from the policy, as the git step's bound
  already does (`heartbeat_seconds`): the shipped value stays one minute, and the tests that wait it out
  set a short one. A timeout's value is not a command, so replay is unaffected; task 1 proves that
  against `tests/histories/`.

## Non-goals

- No new test framework or dependency: no pytest, pytest-xdist, pytest-testmon, Pants or Bazel (see
  [Alternatives](#alternatives-considered)).
- No parallelism inside a process: its tests share one Temporal test server and its workers by design
  ([tests/temporal_env.py](../tests/temporal_env.py)); classes run apart only as separate processes.
- No running the two hosts' suites at the same time: they share localhost's test ports
  ([tests/README.md](../tests/README.md)).
- No CI change: the suite drives real processes and a PTY and runs on a real host (`AGENTS.md`).
- No stored timings or cache between runs.

**Industry practice (sources in [Review record](#review-record))**

- *Test impact analysis* is the standard for fast iterations: run the tests a change can reach, and the
  whole suite at the merge gate. Two families: dynamic, coverage-traced (pytest-testmon), and static,
  import-graph (Pants `--changed-since=<ref> --changed-dependents=transitive test`, pytest-impacted).
- Pants' own guidance: files import inference cannot reach — configuration, data — need explicit edges;
  a lockfile change counts as changing every user of it. That is A1's fallback to the whole suite.
- Process parallelism at the level of the suite's fixtures is the standard: module or class
  (unittest-parallel's `--level=module|class`; pytest-xdist's `--dist loadfile|loadscope`).

**Inferences**

- Modules in parallel: a whole run floors at `test_stops`' 210 s. Classes in parallel: at `Stop`'s
  159 s. With A5 as well, `Stop` falls to about 21 s plus its short bounds, and the floor becomes
  `test_launch.StartupDeath`'s 40 s — a whole run near a minute, provided the load does not stretch the
  timed tests.
- A static import graph selects little in this suite (measured below): the harness every Temporal-backed
  module shares imports `application.activities` and `interfaces.cli`, and through them nearly all of
  `app/`.

**Assumptions / unverified**

- That the 14 timed assertions and `test_harness`'s exit bound hold at A2's concurrency: verified only by
  task 4's repeated runs.
- That `test_launch`'s scopes (`systemd-run --user`) and Windows job objects tolerate concurrent use by
  two modules: to verify in task 4.

## Current architecture and source of truth

- [tests/__main__.py](../tests/__main__.py) owns how the suite runs in a process: `unittest.main`, then
  the exit watchdog. It is the one runner both hosts use, through `run-tests.sh` and `run-tests.ps1`,
  which own the environment (`uv sync --locked`, `envpath.py`) and, on Windows, the host list.
- [tests/test_architecture.py](../tests/test_architecture.py) owns the package graph and its import walk.
- [tests/README.md](../tests/README.md) owns how to run the suite and what each module guards.

## Problem and root cause

Every run is serial and whole: `unittest discover` runs 17 modules one after another in one process,
so a run costs the sum of the modules (469 s), however small the change. The runner has no notion of
what a change reaches, so an iteration on one module pays for all of them, and review loops repeat that
cost each round.

## Decision

Take the two real-clock waits out of the tests, then extend the existing runner, `tests/__main__.py`;
the scripts pass its modes through.

0. **The Stop cleanup's bound from the policy (A5)**, so the tests that meet it set a short one, as the
   git step's tests already do.
1. **Parallel (D1).** `python -m tests --parallel [modules…]`: each test class (A4) runs in its own
   `python -m tests <module.Class>` subprocess — its own interpreter, test server and exit watchdog — at
   most A2 at once. Each process's output is printed
   whole when it ends, never interleaved; a summary lists every class's result and time; the exit code
   fails if any failed, errored or hung. With no modules named it discovers them as `discover` does.
2. **Selection (D2, D3) — held by Q3.** `python -m tests --changed [--since <ref>]`: the changed files (A3) are read
   from git; a static graph of imports over `app/` and `tests/` — the same AST walk
   `test_architecture.py` uses, extended to the harness's own root modules — gives each test module the
   files it reaches. A module runs when a changed file is among them. A changed file no module's graph
   contains (A1) runs the whole suite, and the runner says which file forced it. The selection is
   printed before it runs, and it runs in parallel.
3. **Make and the scripts.** `make test` runs the whole suite in parallel; `make test-changed` runs the
   selection. `run-tests.ps1` intersects a selection with its host list.

The whole suite on each host a change touches stays the gate before a change is called done (`AGENTS.md`);
the selection is the loop before it.

### Premise / KISS gate

- **Owner.** `tests/__main__.py` already owns "how the suite runs"; `test_architecture.py` already walks
  imports. Both are extended; nothing new owns either concern.
- **Adds.** Two flags in one runner, one subprocess per test class, one graph walk over files already
  parsed by the architecture test. No service, port, daemon, cache or dependency.
- **Removes.** The serial wait; two tests' minute-long waits on a production constant; under Q3 (a),
  the hand choice of which modules to run while iterating.
- **Given up.** Test-level precision: a selected module runs whole even if one of its tests is affected
  (pytest-testmon's coverage tracing could skip more); and a dynamic trace of subprocesses — scripts,
  the PTY host, the agents — which the static graph replaces with "unattributed means everything".

### Alternatives considered

- **pytest + pytest-xdist + pytest-testmon.** The most precise selection, but three new dependencies, a
  second runner beside unittest, a coverage database to keep, and coverage does not follow the suite's
  subprocesses (workers, PTY host, fake agents) without extra configuration — exactly where this suite's
  risk lives.
- **Pants or Bazel.** Build systems whose `--changed-since` is the reference for this practice; adopting
  one for a 17-module suite is far out of proportion.
- **unittest-parallel.** Module-level parallelism with no selection, and a dependency for what one
  subprocess pool gives.
- **A hand-kept map of package → test folders.** A second source of truth, and wrong today: the client
  and activities are proven by other folders' tests.

## Required invariants

1. A selection never runs less than a change reaches: any changed file outside the graph runs the
   whole suite.
2. The whole suite on each host a change touches remains the completion gate (`AGENTS.md`).
3. Every process keeps its own test server and exit watchdog (D15's lesson: a hang names its thread and
   is never hidden), and a class's tests still run in one process, in their order.
4. A failure, error, hang or crash of any module fails the run; nothing is retried.
5. A test that fails only under parallel load is a defect to root-cause, never a reason to lower
   concurrency silently or rerun until green.
6. The two hosts' suites still run one after the other.
7. No new dependency; `uv.lock` unchanged.

### 2026-09-23 — Q3: the industry's practice, as a suggestion for the reviewer

- **Trigger:** the operator asked how the best industrial teams do it, then: *"record as suggestion to
  reviewer investigate should separately"*. Q3 stays open; the reviewer investigates it independently.
- **What was found:** every large shop layers its testing — the developer runs what they touched, a
  selection runs before merge, the whole suite runs after — and keeps the whole suite as the gate.
  Google's TAP selects the test targets its build graph says depend on the changed files; that is
  precise because its targets are fine-grained. Meta adds a model trained on past failures on top of the
  graph, which halved its testing cost while still reporting over 99.9% of faulty changes — a scale of
  tests and history this repository does not have. Coverage-traced selection (Microsoft's test impact
  analysis, pytest-testmon) follows only the code a test's own process runs. Parallel shards come before
  selection. Here, one shared harness that imports nearly all of `app/` is what makes an import-graph
  selection coarse.
- **Sources:** [Software Engineering at Google — continuous integration](https://abseil.io/resources/swe-book/html/ch23.html),
  [Taming Google-scale continuous testing](https://research.google.com/pubs/archive/45861.pdf),
