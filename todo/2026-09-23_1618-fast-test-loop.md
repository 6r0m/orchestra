## Goal

An iteration on a change runs, in seconds rather than minutes, only the test modules it touches, named to
the runner; and a whole run takes about as long as its slowest parts, not the sum of all of them.
Measured per host: its wall time, its slowest class and its summed class time.

## Authority register

### Operator decisions

- **D1** Run the suite's modules in parallel.
  - Effect: `make test` and the host suites run concurrently rather than one after another.
  - Reason: not stated; asked after a full run of the suite had taken about eight minutes per review round.
  - Date/source: 2026-09-23, operator — *"we need yes parallel run"*
- **D2** Run the whole suite when core code changed; otherwise only the exact modules the change affects.
  - Effect: met by naming the modules a change touches (D4).
  - Reason: not stated.
  - Date/source: 2026-09-23, operator — *"run all suite if core changed otherwise only exact modules"*
- **D3** An iteration does not run the huge checks every time: only the scope of the module being
  changed, following the industry's standard practice for quick, quality iterations. The whole suite runs
  once, at the reviewer's final pass, before the operator's live checks.
  - Effect: the named run is the inner loop; the whole suite is the gate at the end of a change.
  - Reason: *"quick and quality iterations"*
  - Date/source: 2026-09-23 and 2026-09-24, operator — *"no need every time run full suite only when

- **D4** No automatic selection: the suite's classes run in parallel, and while iterating the modules a

  - Effect: closes Q2 and Q3; the import-graph selection and a `make test-changed` are not built.
  - Reason: *"while we not hit again in wall of indefinite testing"*
  - Date/source: 2026-09-24, operator — *"ok pick c"*, the investigation's and the audit's recommendation

### Working assumptions

- **A2 [ACTIVE]:** at most `min(cpu count, 8)` classes at once, so the wall-clock bounds some tests
  assert keep their margin.
- **A4 [ACTIVE]:** what runs in its own process is a test class, not a module: `test_stops` alone takes
  210 s, so modules in parallel could not bring a whole run under about three and a half minutes.
- **A5 [ACTIVE]:** a Stop's cleanup bound, `STOP_CLEANUP`, comes from the policy as an optional key, read
  with today's minute as its default: every recorded and in-flight run carries no such key and keeps
  exactly today's command, so no `workflow.patched` is needed, and the shipped `policy.json` leaves it
  out. The tests that wait it out set a short one. Task 0 proves it on `approval_stop.json`, the one
  history that reaches a Stop's cleanup.

## Non-goals

- No automatic selection of what to run (D4).
- No new test framework or dependency: no pytest, pytest-xdist, pytest-testmon, Pants or Bazel.
- No parallelism inside a process: its tests share one Temporal test server and its workers by design
  ([tests/temporal_env.py](../tests/temporal_env.py)); classes run apart only as separate processes.
- No running the two hosts' suites at the same time: they share localhost's test ports.
- No CI change: the suite drives real processes and a PTY and runs on a real host (`AGENTS.md`).
- No stored timings or cache between runs.

## Verified evidence

- The runner is `unittest`, one process: `run-tests.sh` runs `python -m tests discover -s tests -p
  "test_*.py" -t .`; `tests/__main__.py` is `unittest.main` plus an exit watchdog armed after the tests
  finish. `run-tests.ps1` passes a fixed list of 14 host modules; named tests replace the list.
- `run-tests.sh` appends named tests to `discover`, so a name becomes its start folder or pattern: one
  named module runs its whole folder, two run nothing; and `tests/__main__.py` counts a run of no tests
  as a success.
- Full WSL suite, serial: 388 tests in 469 s. Each module alone on WSL (16 cores): `test_stops` 210 s,
  `test_launch` 59, `test_terminal` 48, `test_workbench` 46, `test_observability` 34, `test_workflow`
  34, `test_worktrees` 28, the other ten under 10 each; summed 491 s, each process paying its own
  interpreter and test server.
- Per class: `test_stops.Stop` 159 s over 13 tests; `test_workbench.Runs` 40; `test_launch.StartupDeath`
  40; `test_terminal.Turns` 28; `test_stops.FinalGate` 21; every other class under 17 s.
- Two tests are 138 s of `Stop`'s 159: `test_a_stop_while_a_git_step_waits_for_a_worker_that_is_gone…`
  (78 s) and `test_a_run_whose_host_has_no_worker_ends_stopped_without_waiting_for_one` (60 s). Both wait
  out `STOP_CLEANUP = timedelta(minutes=1)` ([workflow.py](../app/orchestration/workflow.py)); the
  time-skipping server does not skip time while an activity sits unstarted, which is why the git step's
  bound already comes from the policy's `heartbeat_seconds`.
- Each test process starts its own time-skipping server (`temporal_env.env()`), so processes share no
  Temporal state. `test_workbench` binds 18490 once per process and four of its classes use it, so
  processes per class would collide there; `test_terminal`'s 18391 is bound by one class, 18390 never.
  Every other test picks a free port; the stack's lock is per test.
- A stage's settings folder is named with the live process's pid, and a sweep takes only a dead pid's,
  so one process's sweep never takes another's folder.
- 14 assertions bound wall-clock time; `tests/test_harness.py` bounds a child's exit.
- Why not select (D4): a static import graph would select, for every `app/` file but
  `workbench/server.py` and three nothing imports, 7–15 modules and 68–96% of the serial time, always
  with `test_stops` — `application/activities.py`, which the test workers need, reaches nearly all of
  `app/`. Coverage-traced selection cannot see the subprocesses where this suite's risk lives. Large shops
  shard in parallel before they select, and select well only where targets are fine-grained.

**Inferences**

- Classes in parallel with task 0: `Stop` falls to about 40 s — its merge test keeps a 15 s wait and a
  3 s sleep — and the whole run to about a minute or a minute and a half, given ~90 class processes of

## Current architecture and source of truth

- [tests/__main__.py](../tests/__main__.py) owns how the suite runs in a process. It is the one runner
  both hosts use, through `run-tests.sh` and `run-tests.ps1`, which own the environment
  (`uv sync --locked`, `envpath.py`) and, on Windows, the host list.
- [tests/README.md](../tests/README.md) owns how to run the suite and what each module guards.

## Problem and root cause

Every run is serial and whole: `unittest discover` runs 17 modules one after another in one process, so
a run costs the sum of the modules (469 s); naming a module to `run-tests.sh` does not run just it; and
two tests wait out a real minute each on a production constant.

## Decision

0. **The Stop cleanup's bound from the policy (A5)**, optional and defaulting to today's minute, so the
   tests that meet it set a short one, as the git step's tests already do.
1. **Parallel (D1, D4).** `python -m tests --parallel [names…]`: each discovered test class (A4) runs in
   its own `python -m tests <module.Class>` subprocess — its own interpreter, test server and exit
   watchdog — at most A2 at once. Each process's output goes to a file and is printed whole when it
   ends, never interleaved; a summary lists every class's result and time; the exit code fails if any
   failed, errored or hung. The parent bounds each child: one still alive past its limit has its output
   printed, its process tree ended, and fails; an interrupted run ends every child's tree. A module that
   fails to load runs as one entry and fails; a run whose count of tests is zero, or differs from what
   discovery found, fails. Named tests are taken as unittest names; with none named it discovers them.
2. **Make and the scripts.** `make test`, `run-tests.sh` and `run-tests.ps1` run it, passing names
   through.

The whole suite on each host a change touches stays the gate before a change is called done — run once,
at the reviewer's final pass (D3, `AGENTS.md`); the named run is the loop before it.

### Premise / KISS gate

- **Owner.** `tests/__main__.py` already owns how the suite runs; it is extended, and nothing new owns it.
- **Adds.** One flag, one subprocess per test class, a limit per child. No service, port, daemon, cache or
  dependency.
- **Removes.** The serial wait, and two tests' minute-long waits on a production constant.
- **Given up.** Automatic selection (D4): whoever iterates names the modules.

### Alternatives considered

- **pytest + pytest-xdist + pytest-testmon.** New dependencies, a second runner, a coverage database, and
  coverage does not follow the suite's subprocesses.
- **unittest-parallel.** Runs classes in parallel processes too (`--level=class`), but has no time limit —
  a hung class holds the whole run, where ours dumps its stacks, ends its process tree and fails it
  (invariant 2) — and it only discovers, never taking exact unittest names. It would add a dependency and
  still need our own wrapper for both.
- **Import-graph selection.** Selects nearly everything here (see the evidence); not built (D4).

## Required invariants

1. The whole suite on each host a change touches remains the completion gate (`AGENTS.md`).
2. Every process keeps its own test server and exit watchdog, and a hang is bounded by the parent, which
   prints it and ends its tree — the lesson of [the Workbench change's exit hang](done/2026-09-21_1237-workbench-controls.md):
   a hang names its thread and is never hidden. A class's tests still run in one process, in their order.
3. A failure, error, hang or crash of any class fails the run; nothing is retried.
4. A test that fails only under parallel load is a defect to root-cause, never a reason to lower
   concurrency silently or rerun until green.
5. The two hosts' suites still run one after the other.
6. No new dependency; `uv.lock` unchanged.
7. A run never reports success for fewer tests than it was asked to run.
